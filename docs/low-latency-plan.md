# 接近物理副屏体验的低延迟实施方案

日期：2026-09-10。状态：待执行；以下数字是项目目标，不是行业统一标准或已实现结果。

## 目标与边界

优先满足办公、代码编辑、拖窗口、滚动网页和视频播放。保持真正的单块 1920×1080、60 Hz 扩展桌面，不以降低到 30 fps 达标。先验证小米 15S Pro，再独立验收三星 Tab S4。暂不承诺电竞屏级响应、HDR、无损色彩或触控回传。

| 项目 | 第一轮可用门槛 | 接近物理副屏的最终目标 |
|---|---|---|
| 画面延迟 | 相对同场拍摄物理参考屏，P50 ≤35 ms、P95 ≤50 ms | 相对参考屏 P50 ≤16.7 ms、P95 ≤33.3 ms、P99 ≤50 ms |
| 输入到显示 | 建立实测基准并报告分布 | 按键/鼠标动作到手机可见变化，P95 ≤50 ms；必须单独测量 |
| 动态流畅度 | 连续 5 分钟动态画面，无持续积压 | 连续 30 分钟；≥99% 的 1 秒窗口呈现至少 57 个不同源帧；无超过 100 ms 的非预期冻结 |
| 画面正确性 | 无持续花屏和参考帧错误 | 动态转静态后不残留损坏；100% 缩放常用字号可读，滚动文字不持续模糊 |
| 稳定性 | 能重复开始/停止 | 20 次开始/停止、10 次拔插和前后台切换，成功恢复；就绪后 3 秒内恢复画面 |
| 持续运行 | 记录温度、功耗、掉帧 | 2 小时无崩溃、无持续增长的帧队列；最后 10 分钟仍达性能门槛 |

相对参考屏的延迟不等于绝对显示延迟。物理参考屏自身有延迟，必须记录其刷新率、模式和测试渲染方法。源帧率、解码回调和真正可见的不同帧不能互相替代。若 Tab S4 无法达标，保留实际数据并明确能力上限，不降低门槛后声称通过。

## 已知基线与代码证据

现有真实链路已通过：IDD 扩展桌面 → Desktop Duplication → CPU 像素处理 → NVIDIA H.264 → ADB USB → Android MediaCodec。用户确认手机看到扩展桌面。

30 秒短测去除前 5 次采样后：平均解码 59.98 fps、呈现回调 59.94 fps；USB 往返平均 6.93 ms、最大 47.56 ms。不是持续动态测试，也没有端到端延迟基线。

1. `native/pc/Protocol.cs`：AnnexBFramer 在收到下一帧 AUD 时释放前一帧。连续均匀 60 fps 输入下可能增加约 16.7 ms，需阶段时间戳实测。
2. `native/pc/Engine.cs`：捕获后 hwdownload、CPU 色彩转换/缩放，再硬件编码；虚拟屏本来就是 1080p，存在消除搬运和冗余处理的空间。
3. LatestFrameMailbox 丢弃的是已编码帧。普通 P 帧可能被后续帧引用，丢帧不保证解码正确；需要改为编码前丢帧和可恢复的过载处理。
4. 20 Mbps 对应 20 Mb VBV，即一秒码率容量。它不等于实际延迟一秒，但应对比小 VBV。
5. 安卓读取线程等待解码输入缓冲最长 1 秒；这不是固定每帧延迟，却可能在堵塞时拖慢读取与反馈。呈现统计回调绑定 UI 线程，存在统计延后。
6. 发送时间戳在编码后才生成；当前无法分离捕获、编码、发送和显示的时间。

## 分阶段实施

### P0：先建立能比较改动效果的测量，阻止错误帧积压

- 新增带唯一帧号、移动条纹、滚动文字和按键变色的测试窗口，放在真实扩展屏中；不使用独立测试视频绕过桌面捕获。
- 协议增加版本、源帧 ID、源时间戳和阶段时间戳；记录捕获完成、编码提交/完成、排队、发送、手机接收、解码提交/输出和呈现通知。
- PC/安卓使用各自单调时钟。通过多轮往返估算时钟偏移和不确定性，不能直接相减两个设备的时钟；不把 RTT/2 当实测单程延迟。
- 手机将帧 ID 映射到解码 PTS，记录回调携带的时间而非 UI 收到回调的时间。统计重复帧、丢帧、恢复次数和队列年龄。
- 用外部 240 fps 或更高帧率录像同时拍参考屏和接收屏，记录拍摄精度及扫描误差；独立拍摄输入动作到画面变化。缺少拍摄设备时只报告内部链路耗时，物理体验验收保持待完成。
- 优先停止任意丢弃编码帧：暂时使用有界队列，过载则结束并重建会话，从有效参数集/IDR 恢复；之后移到编码前丢旧帧。不得让队列无限增长。
- 产物：测试窗口、版本化统计、分析报告和可重复执行的基线命令。

### P1：现有链路快速优化，每项独立 A/B

- VBV 分别试 1、2、4 帧容量（20 Mbps/60 fps 下约 333、667、1333 Kb），保留原配置作为对照；同时测文字质量和复杂场景，不能只看静态壁纸。
- 保留现有无 B 帧、无 lookahead、超低延迟编码设置；不重复把这些已启用的选项算作新收益。
- 移除匹配 1080p 时不必要的缩放和填充。测试同显卡编码器，分别比较 QSV 与 NVENC 的完整路径，而非只比较编码器孤立速度。
- 安卓采用独立统计线程；网络读取与解码输入解耦但严格限制队列。过期显示输出可以不呈现，仍需正确处理解码参考关系。
- 只依据队列实测调整 USB 发送缓冲，避免盲目缩小后增加阻塞。ADB 继续保留。
- 通过条件：相同动态负载下延迟分布改善且画质/稳定性不退化；不改善的参数撤回。

### P2：原生编码输出，去掉等待下一帧和 CPU 往返

- 新增原生视频后端：取得 D3D11 纹理，在 GPU 转换为 NV12，提交给硬件编码器；完成一帧就输出一个明确长度的视频包。
- 使用编码器 API 的完成事件/输出包边界，替代依靠下一帧 AUD 切分的 stdout 字节流。FFmpeg 命令行路径保留为兼容回退。
- 编码前只保留最新待处理原始帧；限制正在编码帧数量。已经提交的编码帧保持引用顺序，拥塞严重时请求 IDR 并重新同步接收端。
- 先在当前电脑比较同 GPU 路径；跨显卡共享不可用时明确标记回退成本。不能以零拷贝名义隐藏跨 GPU 或 CPU 拷贝。
- 通过条件：无下一帧等待、GPU 路径无 CPU 原始像素下载、队列年龄有界，并通过第一轮延迟门槛。

### P3：IDD 纹理直接交给独立编码进程

- 在 IddCx 帧处理处取得纹理，将画面复制到自有的有界共享纹理池，再及时归还系统缓冲；不能在驱动中等待手机或 USB。
- 驱动与编码进程之间定义共享句柄、帧 ID、格式、尺寸、显卡 LUID、同步对象和生命周期。只允许本机授权进程访问。
- 处理纹理同步、设备丢失、分辨率变化和进程退出。进程崩溃不能令驱动持续占用交换链。
- 对比 P2：只有测得额外收益且稳定性通过，才默认启用直连路径。
- 通过条件：30 分钟动态及 2 小时稳定性测试；接近物理副屏的目标通过外部录像验证。

### P4：设备验收与日常使用

- 在 Tab S4 独立测试解码能力、刷新率、发热和前后台恢复；选择其支持的模式，不能假设它具有小米的低延迟能力。
- Windows 界面提供兼容/低延迟模式，自动选择屏幕、显卡和编码器；状态明确区分配置 60 Hz、实测 fps 和已测延迟。
- 完成拔插恢复、显示布局恢复和失败回退。驱动正式签名/分发单列，不与性能验收混为一谈。
- 只有测得 USB 本身为主要瓶颈时，才评估 AOA/WinUSB 替代 ADB；不会先重写传输层。

## 决策与测试规则

每阶段单独提交并保存前后报告。固定相同分辨率、设备、USB 线、刷新率和电源条件，预热后至少做三轮；同时报告 P50/P95/P99、冻结、画质和资源占用，不能只选最好的一次。

顺序为 P0 → P1 → P2 → P3 → P4。P2 若已满足体验门槛，P3 可作为后续优化，避免为架构复杂度牺牲稳定性。优先解决延迟长尾和正确性，再追求最低平均值。不预估无证据的毫秒收益，也不承诺在所有设备上等同物理屏。
