# VBV 实机对照：2026-09-11

结论：未观察到小 VBV 对发送到呈现回调确认延迟的一致改善，保留默认 20 Mb VBV。不能据本实验判断编码耗时或完整显示延迟的改善。

设备：小米 15S Pro（25042PN24C），本机 NVENC、1920×1080/60、20 Mbps、ADB USB。真实虚拟桌面显示动态帧号窗口。四档各三次有效测试，每次约 60 秒；第二轮反向排序。第三轮 1 帧档首次启动过载，记录失败后同配置补跑剩余三项。共 13 次尝试、12 次完成。

统计去掉编码序号小于 300 的确认帧，近似预热五秒。下表是每次测试的发送到回调确认分位数，单位 ms，不是各次分位数再合并。

| VBV | 第一次 P50 / P95 | 第二次 P50 / P95 | 第三次 P50 / P95 |
|---|---|---|---|
| 默认 20 Mb | 20.80 / 29.88 | 51.80 / 90.86 | 28.03 / 49.08 |
| 1 帧 333334 bit | 56.20 / 118.83 | 27.93 / 47.57 | 43.88 / 86.49（补跑） |
| 2 帧 666667 bit | 27.95 / 49.15 | 35.35 / 64.16 | 50.59 / 96.47 |
| 4 帧 1333334 bit | 43.03 / 75.88 | 46.57 / 88.63 | 20.55 / 28.03 |

完成的各次测试预热后平均解码约 59.93–60.15 fps。这是回调统计，不能证明每秒呈现了 60 个不同源画面。用户在前几轮反馈没有明显花屏、模糊或长时间停住，不能替代逐轮客观画质验收。

## 限制与失败

- 指标从编码后发送开始，包含确认返回的耗时；不包含桌面捕获、编码和等待下一帧 AUD 的时间。VBV 可能改变输出节奏，但本测量无法直接归因。
- Android 报告的呈现时间戳仍与本地计时不一致，所有对应绝对呈现时间差均判为无效；仅使用 PC 本地发送到确认时间。
- 不同轮次波动明显，不能从某次最优值推断某档稳定更快。尚未控制热状态、后台调度或屏幕刷新相位，也未使用外部录像。
- 第三轮 1 帧配置发送 4 帧后触发四帧队列过载，安全终止。补跑成功。只能确认存在偶发启动问题，不能断定由该 VBV 档导致。
- 没有增大帧队列或改变默认编码参数来掩盖失败。

接下来优先定位启动帧突发和接收回调排队，补齐捕获/编码阶段的时间标记，再推进原生编码包输出以移除 AUD 下一帧等待。总延迟验收仍需外部测量；当前未达到物理副屏体验验收结论。
